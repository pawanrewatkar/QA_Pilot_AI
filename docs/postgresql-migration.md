# PostgreSQL schema and migration plan

Status: **prepared and tested in a disposable in-process PostgreSQL (PGlite) only.** Nothing here has been run
against a hosted database. The app still runs on SQLite (`DATABASE_PROVIDER=local`), and selecting
`DATABASE_PROVIDER=supabase` still fails closed ("not implemented yet"): about 50 repository methods and the worker
still use the SQLite connection directly. See "Prerequisites" before any hosted setup.

## Schema decisions

The PostgreSQL schema is a mechanical translation of the SQLite schema after SQLite migrations 1–7, limited to what
the compatibility tests verified:

- **Types kept as the repositories expect them today.** Timestamps stay ISO-8601 UTC text; JSON stays in TEXT
  columns; ids stay TEXT (UUIDs generated by the app); booleans stay 0/1 integers. Native `timestamptz`, `jsonb`,
  `uuid` and `boolean` are a later decision (they change what the repositories receive).
- `REAL` → `DOUBLE PRECISION`. `INTEGER` → 4-byte `integer` (every value the app writes fits; the importer checks
  every row). `rowid` columns are 8-byte.
- **Defaults:** `strftime('%Y-%m-%dT%H:%M:%fZ','now')` → `to_char(now() AT TIME ZONE 'UTC', …)`, producing the same
  text (`2026-03-01T10:00:00.000Z`).
- **Case-insensitive index** `projects(name COLLATE NOCASE)` → `projects(lower(name))`.
- **Insertion order (pending approval).** 15 tables get `rowid BIGINT GENERATED BY DEFAULT AS IDENTITY`. Their
  queries break ties with SQLite's implicit `rowid`; with a column of the same name the SQL needs no change and the
  order is identical (proven by the compatibility tests). The import copies each row's SQLite rowid and moves the
  identity sequence past it. Alternative: a differently named column (e.g. `seq`) and SQL changes in ~25 places.
  Tables: projects, documents, test_configurations, test_runs, test_results, activity_log, crawl_runs, jobs,
  reports, report_bundles, external_test_executions, bugs, bug_evidence, bug_occurrences, bug_status_history.
- **Authorization boundary.** Ownership is unchanged (`projects.owner_id`; everything else reaches its owner through
  `project_id` / `test_run_id` with the same foreign keys and cascades), and the app keeps enforcing it server-side.
  In addition, **row-level security is enabled on every table with no policies**: Supabase's `anon` and
  `authenticated` roles (its public Data API) get no rows and cannot write, even if granted access. The app
  connects as the table owner, which RLS does not restrict. (Tested with a separate role in PGlite.)
- SQLite's `schema_migrations` table is not copied; `qa_pilot_migrations` tracks PostgreSQL migrations.
- `test_credentials` stores a username and a `secret_ref` (a reference, not a secret); it is not used by the app yet.

### Incompatibilities found and how they are handled

| SQLite behaviour | PostgreSQL | Handling |
|---|---|---|
| Implicit `rowid` | No equivalent | Identity column on 15 tables (pending approval); rowids preserved on import |
| Dynamic typing (any value in any column) | Strict types | Pre-flight rejects values of the wrong type (e.g. binary data in TEXT) |
| 64-bit INTEGER | `integer` is 32-bit | Pre-flight rejects out-of-range values |
| TEXT may contain NUL characters | Not allowed | Pre-flight rejects them |
| CHECK constraints can be bypassed (`ignore_check_constraints`) | Always enforced | SQLite's integrity check reports such rows during pre-flight |
| Foreign keys can be off | Always enforced | Pre-flight runs `PRAGMA foreign_key_check` |
| `strftime` defaults | `to_char(now() …)` | Same text format; tested |
| `COLLATE NOCASE` | Not available | `lower(name)` index; the case-insensitive *sort* in the projects list is still SQLite-only |
| JSON functions, `SUM(boolean)`, case-insensitive `LIKE`, NULL ordering | Different | Fixed in the migrated repositories (Phase 3.3a); unverified in the methods still on SQLite |
| Text sorting is byte-wise | Locale collation | Validation orders by `COLLATE "C"`; app-level sorting is out of scope for now |

## Migration tracking and ordering

- Files are `NNNN_name.sql`, numbered from 1 without gaps; tables in each file are in foreign-key order.
- `qa_pilot_migrations(version, name, checksum, applied_at)` records each applied file. The checksum ignores line
  endings (CRLF vs LF checkouts).
- Before applying anything, every recorded migration must exist in the code with the same checksum. An edited file
  or a database that is ahead of the code stops the run. Never edit an applied migration; add a new one.
- Each migration runs in one transaction together with its tracking row (PostgreSQL DDL is transactional): it is
  applied completely or not at all, and a failure stops the run with earlier migrations kept.
- A transaction-scoped advisory lock serializes concurrent runners and works through Supabase's transaction-mode
  pooler; each version is re-checked under the lock. (PGlite cannot run two real connections, so true concurrency
  is verified only by that re-check.)

## Data migration (only if existing SQLite data must move)

Done once, at cutover, with the app stopped. The importer is a library on purpose: it must only ever read a **copy**.

1. **Freeze.** Stop the web app and the worker, so nothing writes to SQLite (data written after the copy would be
   lost).
2. **Copy SQLite.** Make a consistent copy of `data/qa-pilot.db` (with the app stopped, copy the `.db`, `-wal` and
   `-shm` files together, or use SQLite's backup API). Record its SHA-256. Keep the original and the existing
   backups untouched and read-only.
3. **Pre-flight** (`preflightSqlite` on the copy): integrity (including CHECK constraints), foreign keys, integer
   range, value types, NUL characters. Fix problems in the copy only, and record what was changed.
4. **Back up PostgreSQL** (see below), then **migrate the schema** (`scripts/pg-migrate.ts --apply`) into an empty
   database.
5. **Import** (`importSqliteIntoPostgres`): refuses a non-empty target; one transaction; tables in foreign-key
   order; values copied as stored (no transformation is needed with the chosen types); rowids preserved and
   identity sequences moved past them. Any rejected row rolls the whole import back.
6. **Validate** (`validateImport`): for all 34 tables, row counts and a SHA-256 digest of every row (all columns and
   rowid, in primary-key order) must match. Then smoke-test the app read-only against PostgreSQL.
7. **Switch** configuration (`DATABASE_PROVIDER=supabase`, `DATABASE_URL`) and start the app.

## Backup, rollback and recovery

- **Before any hosted migration:** a database backup (Supabase scheduled backup or point-in-time recovery, or
  `pg_dump`), and verify it can be restored.
- **Failed schema migration:** nothing to undo; the failing migration rolled back and earlier ones are intact. Fix it
  with a new migration.
- **Failed import:** nothing to undo; the import rolled back. Fix the SQLite copy and retry.
- **Abandon after a successful import, before cutover:** truncate the app tables (or restore the backup) and keep
  using SQLite.
- **Problems after cutover:** switch back to `DATABASE_PROVIDER=local` with the frozen SQLite copy; anything
  written to PostgreSQL after cutover would have to be reconciled by hand, so keep the observation window short.
- Migrations only move forward; there are no down-migrations. A reversal is a new forward migration, or a restore.

## Separation from deployment

- The app never migrates PostgreSQL on its own. `scripts/pg-migrate.ts` runs explicitly, after a backup, **before**
  deploying code that needs the new schema; migrations must stay compatible with the code that is still running.
- Status is read-only by default; `--apply` is required to change anything.
- The SQLite migrations (`npm run db:migrate`, `lib/database/schema.ts`) are unchanged and separate.

## Configuration and secrets

- `DATABASE_URL` (server-only) holds the PostgreSQL connection string, including the password. It comes from the
  environment or the host's secret manager, never from the repository (`.env.example` has a placeholder only).
- It is never logged or included in error messages (the executor and `scripts/pg-migrate.ts` print error codes and
  names only).
- The app uses the database owner connection server-side; Supabase's service-role and anon keys are not needed for
  database access, and the anon key must never grant table access (RLS above).

## Prerequisites for a hosted database (not done)

1. Approve the insertion-order column design (or choose the alternative).
2. Fix the PostgreSQL executor issue found in the review after Phase 3.3a: a transaction's connection can be reused after it
   is released.
3. Move the remaining SQLite-only code to the SQL executor: ~50 repository methods, every write transaction, the
   worker store, job queue (claiming needs `FOR UPDATE SKIP LOCKED`), bug engine, report loading; and replace their
   SQLite-only SQL (`json_extract`, `IS ?`, `INSERT OR IGNORE`, `PRAGMA`, `COLLATE NOCASE`, `LIKE`).
4. Implement the PostgreSQL `DatabaseProvider` (today it fails closed) and run the full test suite against it.
5. Pool settings: connection and statement timeouts, pool size, SSL, and Supabase pooler mode (session vs
   transaction; the migrator works with both).
6. A Supabase project with backups or point-in-time recovery enabled, a role and connection string for the app
   stored as a secret, and a rehearsal of the whole data migration on a copy against a non-production database.

## Unresolved gaps

- Insertion-order column: designed and tested, not approved.
- Native PostgreSQL types (`timestamptz`, `jsonb`, `uuid`, `boolean`), collation and search behaviour: out of scope
  for now; the schema keeps SQLite-compatible types.
- Untested against a real PostgreSQL server (driver result types, SSL, pooler behaviour, real concurrency).
- SQLite-only SQL in the ~50 methods still on the raw SQLite connection is not yet verified on PostgreSQL.
- The case-insensitive project-name sort (`COLLATE NOCASE` in a query, not only the index) has no equivalent yet.
